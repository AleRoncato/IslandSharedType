# Island Shared Types — Prototype API Design

**Status:** Working draft, not a Working Group–approved specification.  
**Scope:** Island–Chart interface, public response types, and optional state helpers.  
**References:** `Main.pdf` §§4, 4.1, 4.2, 5.3, 6.1–6.2; `Protocol.pdf` §13.5.

> **Status convention**  
> **Required** = specified by Main/Protocol.  
> **Prototype choice** = current design decision used to validate the interface; may change after WG discussion.  
> **Open** = not settled by the documents or this prototype.

## 1. Responsibilities and boundaries

### Chart — authoritative game state

- **Required:** Generate one true, full-strength `Clue` for each Island and provide it at Island construction. The Island does **not** know the Treasure cell.
- **Required:** Own the world and evaluate legality of Ship actions; an Island never interacts with the world directly.
- **Required:** Own the current round and the Ship views/events. Ships cannot invoke Island methods directly.
- **Prototype choice:** Pass a read-only `IslandContext` containing the current round to Island operations.

### Island — policy and internal state

- **Required:** Retain its original Clue; distributing a Clue never consumes it.
- **Required:** Decide *whether, when, and in what strength* its Clue is issued, within the game's fairness constraints.
- **Required:** Decide its mooring/berth policy and the time-based price of information.
- **Required:** Be able to report, **for a given Ship**, both (a) whether it has anything further to offer and (b) remaining waiting time. These are explicit §13.5 trait obligations.
- **Optional by design:** Track visits, departures, previously issued information, and other Ship-specific history.
- **Allowed but not yet modeled:** Hull repairs and information about past visitors.

**Architectural rule:** The shared `Island` trait specifies *observable behavior*. Each concrete Island chooses its internal data structures and may change its strategy dynamically during the game.

## 2. Types owned by other components

## 3. Public Island API types (`src/island.rs`)

### `IslandResponse` — result of requesting a Clue

```rust
pub enum IslandResponse {
    Respond(Clue),
    Wait(u32),
    Refused,
    NothingMore,
}
```

| Variant | Meaning | Intended use |
| --- | --- | --- |
| `Respond(Clue)` | The Island delivers a Clue, possibly weakened | Successful `ask_clue` after its required wait |
| `Wait(n)` | The Clue is not ready; `n` rounds remain | An active, unfinished waiting period |
| `Refused` | The Island refuses this request | For example, the Ship is not moored |
| `NothingMore` | No additional useful Clue is available for this Ship | For example, the full-strength Clue was already delivered |

**Required:** The interface must represent Clue, refusal, and “wait `n` rounds.” The returned Clue must have the same variant/kind as the original, and weakening must preserve truth.  
**Prototype choice:** `NothingMore` is a fourth, explicit status. Whether it should instead be represented as a reason for refusal is **open**.

### `MoorResponse` — outcome of attempting to moor

```rust
pub enum MoorResponse {
    Accepted,
    Refused,
    NoSpace,
}
```

- `Accepted`: the Island accepts the Ship; an internal mooring/contract state may be created.
- `Refused`: policy-based refusal (e.g. duplicate mooring or a previously served Ship in the demo).
- `NoSpace`: no berth is available; distinct from a policy refusal.

**Prototype choice:** Separate rejection reasons instead of returning `bool`. Berth limits are not yet implemented in the demo.

### `ClueOffer` — a quoted price

```rust
pub struct ClueOffer {
    pub wait_rounds: u32,
}
```

- `wait_rounds` is the proposed number of waiting rounds for the next information delivery.
- `0` means no additional waiting rounds; `AskClue` is still a game action.
- The offer does **not** reveal the strength of the eventual Clue.
- `quote()` returns `Option<ClueOffer>`: `Some(offer)` means an offer exists; `None` means no new offer is available under the current policy.

**Prototype choice:** The accepted price is recorded when mooring and does not change during that contract. Publishing quotes *before* mooring is an **open integration question** because Ships communicate through Chart/views, not directly with Islands.

### `IslandContext` — information supplied by Chart

```rust
pub struct IslandContext {
    pub round: Round,
}
```

- Read-only snapshot of Chart-provided information for a method call.
- The **Chart** owns the clock; Island implementations do not need separate synchronized global round counters.
- Used to timestamp visits and compute elapsed/remaining wait from contracts.

**Prototype choice:** This replaces `advance_round()` for basic time calculations. The Main also grants Islands a turn on round closure; whether the final trait additionally needs `on_round_end()` is **open**.

## 4. Optional reusable state helpers (`src/history.rs`)

These types can live in the shared library **without being required by the `Island` trait**. A group may use them, extend them privately, or use another representation.

### `IslandHistory` — visit-start log

```rust
pub struct IslandHistory {
    visits: BTreeMap<ShipId, Vec<Round>>,
}
```

| Method | Purpose |
| --- | --- |
| `new() -> Self` | Construct an empty history |
| `record_visit(ship, round)` | Append the starting round of a visit |
| `visits_of(ship) -> Option<&[Round]>` | Read a Ship's recorded visit-start rounds |

**Important:** The current helper records **arrivals only**. It does not yet store departure times, visit durations, Clues delivered, or active berth occupancy. `BTreeMap` gives deterministic key iteration; it does not make a history mandatory.

### `ClueContract` — an accepted waiting period

```rust
pub struct ClueContract {
    pub start_round: Round,
    pub required_rounds: u32,
}
```

For an active contract:

```text
elapsed_rounds   = current_round - start_round
remaining_rounds = max(0, required_rounds - elapsed_rounds)
```

Using `u32::saturating_sub` avoids unsigned underflow; correct chronological order must still be enforced by the caller.

**Prototype choice:** Leaving an Island cancels the active contract and discards unfinished progress, while history remains. An Island may choose a different price on a later visit. This behavior has **not** yet been approved by the WG.

### `ShipState` — not a mandatory shared type

A concrete Island *may* privately store fields such as `active_contract`, `full_clue_received`, or a visit counter. **Do not require one `ShipState` struct in the public trait.** Otherwise every group would be forced into the same internal state model.

## 5. Proposed `Island` trait

```rust
pub trait Island {
    fn quote(
        &self,
        ship: ShipId,
        ctx: &IslandContext,
    ) -> Option<ClueOffer>;

    fn moor(
        &mut self,
        ship: ShipId,
        ctx: &IslandContext,
    ) -> MoorResponse;

    fn leave_berth(
        &mut self,
        ship: ShipId,
        ctx: &IslandContext,
    );

    fn ask_clue(
        &mut self,
        ship: ShipId,
        ctx: &IslandContext,
    ) -> IslandResponse;

    fn remaining_wait(
        &self,
        ship: ShipId,
        ctx: &IslandContext,
    ) -> Option<u32>;

    fn has_more_to_offer(&self, ship: ShipId) -> bool;
}
```

**Status:** The signatures above are the **current prototype proposal**, not the published Protocol interface. In particular, `quote`, `leave_berth`, and the use of `IslandContext` are design choices. The two mandatory capabilities from §13.5 are `remaining_wait` and `has_more_to_offer` (names and exact return types still subject to WG agreement).

### Method semantics

| Method | Reads / changes state | Meaning and expected use |
| --- | --- | --- |
| `quote(ship, ctx)` | Read-only (`&self`) | Calculate a potential price for the next information delivery; does not moor the Ship or create a contract. |
| `moor(ship, ctx)` | Mutating (`&mut self`) | Decide whether to accept an already Chart-validated attempt; on acceptance, register the arrival and any active waiting contract. |
| `leave_berth(ship, ctx)` | Mutating | Notify the Island of a departure; release any internal berth/active contract and optionally record the departure. |
| `ask_clue(ship, ctx)` | Mutating | Evaluate a moored Ship's request; return Clue, remaining wait, or refusal; record successful delivery as needed. |
| `remaining_wait(ship, ctx)` | Read-only | Report the remaining rounds of this Ship's active offer/contract; `Some(0)` means ready, `Some(n)` means still waiting, `None` means no applicable active wait. |
| `has_more_to_offer(ship)` | Read-only | Report whether this Ship may still receive useful information; must be `false` after it has received the full-strength Clue from this Island. |

**Action boundary:** `AskClue` requires the Ship to be moored. Chart is responsible for game-action validation; Island is responsible for its response/policy. A valid `AskClue` can produce `Wait` or `Refused` without the Chart rejecting the action.

**Contract consistency:** A successful `moor` must not silently replace an existing active contract for that Ship. An active wait should be queried with `remaining_wait()`, not recomputed from a new `quote()`.

## 6. Example implementations (tests only)

Two concrete types were used to validate the interface. **They are not prescribed Island categories.** A real Island can change strategy at runtime.

| Behavior | `GenerousIsland` | `GreedyIsland` |
| --- | --- | --- |
| Proposed price | 0 rounds | Example: Ship 0 → 3, Ship 1 → 7, others → 5 |
| Active wait | Immediately ready | One `ClueContract` per moored Ship |
| `ask_clue` before mooring | `Refused` | `Refused` |
| First completed request | `Respond(full_clue)` | `Respond(full_clue)` after the wait |
| Repeated request after full delivery | `NothingMore` | `NothingMore` |
| History | Optional `IslandHistory` | Optional `IslandHistory` |

The demo intentionally issues only full-strength Clues. A more sophisticated Island may issue weakened Clues first, but must still make its full-strength Clue eventually obtainable by every persistently compliant Ship.

### Example timeline

```text
Round 0: Ship 0 moors at GreedyIsland. Contract: 3 rounds.
         ask_clue(Ship 0) -> Wait(3)
Round 2: Ship 1 moors at GreedyIsland. Contract: 7 rounds.
         ask_clue(Ship 0) -> Wait(1)
         ask_clue(Ship 1) -> Wait(7)
Round 3: ask_clue(Ship 0) -> Respond(Clue)
Round 9: ask_clue(Ship 1) -> Respond(Clue)
```

This timeline illustrates **independent per-Ship waiting periods**. It is a logical API demonstration, not a literal replay of a full Chart turn schedule (a Ship gets one game action per round).

## 7. Non-negotiable game rules

These rules follow Main/Protocol; they are not optional implementation strategies.

1. Each Island receives **one genuine Clue**, generated by Chart; it does not know the Treasure position.
2. A returned Clue must be **truthful**, **the same kind/variant** as the original, and either the original or a valid weakening. Never strengthen the original.
3. The original Clue is **never consumed** by issuance.
4. No permanent stonewalling or exclusivity: a Ship that repeatedly returns and complies with the requested waits must eventually receive the **full-strength Clue**, as must any other compliant Ship.
5. An Island can repair a Ship but **must never damage** it.
6. Ships must be **moored to request a Clue**; Islands are owned/invoked synchronously by Chart, not called directly by Ships.
7. The two per-Ship information capabilities—**nothing more to offer** and **remaining wait**—must appear in the shared trait.

## 8. Open design decisions for the WG

1. **Information exposure:** Must a Ship moor before it can learn prices or available services? If not, which data may appear in `ShipView`, and under what visibility rules?
2. **Quote guarantee:** When exactly is a price fixed? Can it change before acceptance? How is it communicated through Chart?
3. **Berth ownership:** Does Chart maintain authoritative occupancy while Island decides admissions, or does Island own occupancy internally? How do we keep both views synchronized?
4. **Round lifecycle:** Is `IslandContext { round }` sufficient, or is an explicit `on_round_end(ctx)` method necessary for time-driven strategies?
5. **Repeated requests:** May a Ship obtain successive weakened Clues during a single mooring? Is a new offer/contract needed between requests?
6. **Leaving early:** Should an unfinished wait reset, persist, or depend on Island policy?
7. **Clue progression:** Must successive weakened Clues be strictly stronger, or is eventual full-strength delivery the only mandatory progression constraint?
8. **Optional services:** How can repairs and visitor-history queries be requested and returned without adding unsupported game actions or violating visibility rules?
9. **RNG and construction:** What initialization data, deterministic randomness, berth capacity, and other parameters must Chart supply?
10. **Outcome shape:** Is `NothingMore` a separate response, or a specific reason for `Refused`?

## 9. File organization and validation

```text
src/
  lib.rs       // export island, history, types
  island.rs    // Island trait + public Chart–Island response types
  history.rs   // optional reusable IslandHistory and ClueContract
  types.rs     // temporary placeholders for external shared types
examples/
  demo.rs      // example concrete Islands + mock Chart loop
tests/
  island_contract.rs  // integration tests of the public interface
docs/
  island_api.md
```

**Suggested prototype checks:**

- `quote()` has no observable side effects and its accepted price matches the contract.
- A non-moored Ship cannot obtain a Clue.
- Different Ships maintain independent wait times.
- Repeated `moor()` does not reset an existing active wait accidentally.
- Leaving releases the berth and handles the outstanding contract according to the adopted policy.
- Once the full-strength Clue has been delivered, `has_more_to_offer(ship)` is `false`.
- A changed internal strategy does not violate already accepted contracts (if quote guarantees are adopted).
- The shared crate compiles without knowing any concrete Island implementation.

**Current milestone:** Validate this interface through a small example and tests; do **not** treat the optional helper types or provisional decisions as mandatory requirements for all groups until the WG agrees.
